Debian and RHEL packages, Docker images (`ghcr.io/llmsyscore/llm-systems-manager:v3.0.0`) and the Homebrew tap (`brew install llmsyscore/tap/llm-systems-manager`) follow the same tag. After upgrading, restart the manager and the alarm engine, then push the new agent to every host from **Admin › Agents › Update all**.

## Spotlight

### Tower — an AI assistant that understands your infrastructure

Tower is an AI assistant available on every page (**Alt+T**). It answers your questions and performs actions for the manager, hosts, models, alerts, energy, tool runs and more. It works through a model the gateway is already serving, or through a dedicated Tower model you download from Settings. Enable it in **Settings › Tower assistant**.

- **Ask.** Tower reads host and hardware details, metric history with trends, loaded models and profiles, alarms and alert history with text charts, energy summaries, gateway traffic, recent tool runs, bench speed, service health, logs, configuration, the audit log, jobs, Forecast findings and the manager's own help. It follows the tab you are on, and canned questions get you started.
- **Act, with approval.** Load, unload and wake models, acknowledge, close or resume alerts, start a benchmark, cancel jobs, restart a provider. Every action waits for your approval, the capability level is *Answer only / Answer and act / incl. admin actions*, and each decision is stored in the audit log as `tower via <user>`.
- **Watch.** Tower looks into each new alert, follows a playbook for the common ones, and stores what it found as an insight every user can see. Scheduled and repeating reads run on a timer ("check disk on gpu1 every 15 minutes for two hours").
- **Question prompts** with choices, tabs and an *Other* option; **model evaluation** and a curated download list in Settings so you can pick a dedicated Tower model; a **Thinking** budget that applies on llama.cpp, LM Studio and vLLM; extra help for small models (host name matching, answer clean-up, a capability check, and hand-off to the fallback model).
- Tower is also available on the **phone companion** (ask, prompts and insights) and through the **Discord bot**.

### Forecast — predictive analysis and trends

Forecast is a scheduled analysis of stored history that reports trends before they become alarms, and works together with Tower when Tower is on. The page is at **Dashboards › Forecast**; the settings are in **Settings › Forecast**.

- **Available checks**: disk fill, load shift, memory headroom, thermal trend, power and cost, throughput, model errors, slot pressure, model churn, alarm patterns, agent health (including clock skew), service health, bench outcomes, capacity, idle waste and an optional weekly digest.
- Findings merge by fingerprint, clear after two clean runs, can be dismissed, and can raise alerts through your normal channels from a chosen severity.
- Two views: **Outlook** (a 30-day line of dated predictions beside a details drawer) and **Briefing** (findings grouped by host or check), with Open / Cleared / Dismissed tabs, filters and search. Each finding offers **Ask Tower** and a jump to the relevant dashboard.
- **Tower effort** (Auto / Off / Light / Standard / Full) sets how much Tower adds to each finding: a digest of the run, a likely cause, a next step, or a closer look with its own tools.
- The **Overall** page shows a strip with critical and warning findings.

### Jobs — one scheduler for everything that runs later

One job service in the manager now runs every deferred or long-running task: Tower timers, overnight autotune batches, tool runs queued behind a busy host, Report Card runs, Forecast and Tower evaluations.

- **Tools queue.** Starting a benchmark, autotune or quality run on a busy host queues the job per host. The queue survives tab close and manager restarts, shows on every dashboard, and can be cancelled by its owner or an admin.
- **Admin › Jobs** ledger with status, kind and user filters, a detail panel with spec, state and result, and Cancel/Dismiss. **System Health** shows live and scheduled jobs.
- Tower can list and cancel jobs; failed jobs also surface in the System Health warnings.

### Live benchmark and a seven-step autotuner

- **Benchmark › Live** runs `speed-bench` against the running server through its API: workload presets (Chat / Coding / RAG / Agentic / Custom), concurrency sweeps, energy per token, and a results chart. Live runs attach to the Report Card, feed Autopilot's cross-host speed ranking, and can be pinned as **baselines** that are re-checked on a schedule with an alarm-engine regression alert. Compare any two ledger runs side by side.
- **Benchmark › Offline** (llama-bench, and now `vllm bench serve`) gains a KV-cache type sweep, energy on every run and a prompt × output heatmap. The old *Batched* mode is retired.
- **Autotune** picks a **goal** (Fit / Speed / Balanced / Serve) and tunes seven settings in order: context, KV cache type (with a quality check), MoE CPU offload, CPU threads, speculative decoding (MTP / DFlash / draft model, with draft discovery on Hugging Face), parallel slots and author-recommended sampling defaults. A recommendation table shows before and after for each setting, and **Verify** loads the result once under traffic.
- **Overnight batch tuning** across models with a summary through the alarm engine, a *Quiet* power-cap goal, a stale-tune reminder with re-verify, and **Quality guard** as a standalone tool.
- **LM Studio and vLLM parity.** Live benchmark and autotune now run on LM Studio hosts; vLLM gets its own autotune settings, Offline bench serve, retries for probe and candidate loads, and a rollback comparison.
- The llama.cpp model editor now has fields for threads, MoE CPU offload and speculative decoding, and a metadata reader fills in author-recommended sampling.

### Performance controller redesign

The host power profile and the model status now follow llama.cpp's state through model swaps, service restarts and agent restarts. The agent checks the model's state every 5 seconds, one controller owns the power switches (a running job outranks a manual choice, which outranks the policy; short changes are waited out and switches are rate-limited and retried), and each switch is read back from the hardware and reported as verified, failed or unverifiable. The installer merges the shipped perf unit files into existing installs with backups.

### Energy per model

Energy, cost and tokens are attributed per model. The **Energy** tab gains a *By model* table (hosts, energy share, residency, tokens, cost, $/Mtok), Tower's energy summary can group by model, and LM Studio tokens are counted per model at the gateway.

## Upgrade notes

- **Restart both services and redeploy agents.** The manager, alarm engine and agent versions all changed.
- **SQLite files renamed and split.** `data/metrics.db` becomes `data/manager.db` on first boot, and the write-heavy `audit_log` and `energy_hourly` tables move to `data/audit.db` and `data/energy.db`. This is automatic and logged once; backups made before the split continue to function.
- **New config sections**, all applied without a restart: `[manager.tower]`, `[manager.forecast]`, `[manager.jobs]`. Both example files, the Settings catalog and the docs were updated together. Deprecated perf-controller keys are ignored with a warning.
- **Perf controller.** The `/tmp` state file and marker config are deprecated; the old keys are ignored with a warning. The example power units now work on hosts without CPU frequency scaling. The installer backs up your existing unit files before merging.
- **Benchmark › Batched is removed**, along with `llama-batched-bench` support. Live mode replaces it.
- **The first Live benchmark on a host needs the bench runtime**, installed with one click from the Benchmark pane (about 150 MB plus 15–100 MB per bench set from the public `nvidia/SPEED-Bench` dataset).
- **InfluxDB memory protection.** The installer adds an OOM-score drop-in and a host-sized `GOMEMLIMIT` for `influxd`.
- **Alarm engine OTLP receiver** now limits how many distinct tag values it keeps per tag; numeric and identifier attributes are stored as fields.
- **Security headers** (`X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: strict-origin-when-cross-origin`, `Content-Security-Policy: frame-ancestors 'self'`) are now sent on every manager response.
